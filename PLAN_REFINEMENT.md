Дата подготовки: 2026-09-05. Документ содержит предлагаемые работы, а не второй реестр статусов. История подтверждений остаётся в [PROGRESS.md](FastAPI/PROGRESS.md); исходный план - [docs/PLAN.md](FastAPI/docs/PLAN.md). После согласования новые задачи следует включить в основной план, устранить дублирование статуса между ним и PROGRESS.md согласно AGENTS.md.

Цель: пользователь входит в приложение, подключает свой Telegram, добавляет канал, получает новые посты в ленте и выбранных интеграциях; расписание работает без открытого браузера, перезапуск не теряет доступ и работу, данные пользователей изолированы.

Согласованный первый релиз: онлайн-приложение для владельца с обязательным входом через Google; Vercel (статика и проксирование), Railway (web, постоянный worker, Postgres). Каналы и группы Telegram, индивидуальные интервал, количество сообщений и промпт; анализ через совместимый с OpenAI API провайдер с выбранной моделью DeepSeek V4 Flash; результаты и история запусков в ленте, настройки сохраняются в Postgres. В дальнейшем сервис открывается другим пользователям: существующую изоляцию тенантов сохраняем сразу. Повторы доставки с дедупликацией в n8n согласованы. Старые настройки, история и Telegram-сессия обязательно переносятся. Модель получает только ещё не обработанные сообщения; прочитанные повторно не передаются. Продуктовые квоты на количество каналов, групп и сообщений не вводятся; ограничения внешних API обрабатываются очередью и повторными попытками.

Google обязателен уже в первой приёмке. Стандартный Firebase SDK выполняет вход, API проверяет Firebase ID-токен и выдаёт собственную сессию. OAuth Web client ID не заменяет FIREBASE_API_KEY и не является ключом сервисного аккаунта. Владелец добавил telegram-monitor-n8n-bridge.vercel.app в Authorized domains и передал конфигурацию Firebase для приложения. Safelist внешних проектов для этой схемы не требуется. Ручная подмена OAuth client ID/secret не нужна для стандартного автоматически созданного клиента; если серверная конфигурация провайдера действительно неполна, сверить соответствующую пару в Google Cloud, не переносить secret в frontend или чат.

Проценты уверенности ниже отражают понимание, а не процент готовности.

## Фаза 1. Исправить раздельный запуск

- Согласовать CSP с реально используемыми шрифтами, скриптами и опциональным Firebase. Предпочесть локальные ресурсы; не отключать защиту глобально.

### 8.4. API, worker и миграции Railway

- Поднять web и worker из одной проверенной версии образа, с разными командами. Начать с одного worker; проверить отсутствие перекрывающихся владельцев MTProto-сессий при redeploy.
- Задать явно раздельные конфигурации сервисов: текущий railway.json содержит web-команду, HTTP healthcheck и preDeployCommand. Воркеру не наследовать web healthcheck и запуск миграций.
- Проверить совместимость DATABASE_URL с asyncpg: код принимает URL без нормализации, а DEPLOY.md предлагает прямую ссылку на переменную Postgres. Использовать проверенный формат postgresql+asyncpg:// или добавить явную валидацию/нормализацию с тестом.
- Только web применяет alembic upgrade head; не редактировать применённые миграции. Проверить версии схемы до запуска воркера.
- Источники: FastAPI/railway.json, FastAPI/app/db.py:25, FastAPI/alembic/env.py, FastAPI/README.md:155, FastAPI/tests/test_70_deploy.py.
- Приёмка: API обслуживает запросы через Vercel, worker выполняет тестовую задачу, перезапуск сохраняет сессию; наличие ответа /health само по себе недостаточно.

### 8.5. CSRF при первом посещении

- Красный браузерный тест: новый профиль сразу открывает ссылку сброса пароля на статическом frontend, затем отправляет форму. Дополнительно проверить быстрый submit входа/регистрации.
- Ввести явное получение CSRF-cookie от API и ожидание завершения инициализации до отправки формы; не зависеть от запроса конфигурации Google.
- Источники: FastAPI/static/js/auth-pages.js:149, FastAPI/static/password-reset.html:66, FastAPI/app/main.py:121, FastAPI/tests/conftest.py:117. Фикстура тестов заранее вызывает /health, что скрывает отличие от статической страницы.
- Приёмка: первый POST проходит в новом профиле; отсутствующий/поддельный CSRF по-прежнему отклоняется; Chrome и Safari проверены через один origin.

### 8.6. Соответствие основному сценарию анализа

- Сохранить согласованный режим: filter_new до LLM, модель получает только сообщения, которые ещё не обработала. Проверить повторный цикл и отсутствие повторного анализа уже обработанных ID.
- Дедупликацию анализа и повторы доставки учитывать отдельно: сбой n8n не должен запускать новый LLM-анализ, а ошибка до анализа не должна помечать сообщения обработанными.
- Проверить влияние offset_hours и сообщений без текста: нынешний limit ограничивает просмотренные сообщения Telegram, поэтому 50 просмотренных не гарантируют 50 текстовых записей для модели. Отображать реальный объём, ограничения и усечение в интерфейсе.
- Отражать каждый запуск расписания со статусом: выполнен, нет новых, отложен Telegram, ошибка LLM или доставки. Исходный текст не показывать как успешный результат анализа при отказе модели.
- Сохранить индивидуальный промпт канала и снимок параметров запуска. Использовать сохранённый base_url и model; фактическую доступность выбранного model ID проверить у настроенного провайдера. OpenAI-совместимый формат запросов не означает вызов серверов OpenAI.
- Источники: FastAPI/app/worker.py:325, FastAPI/app/services/messages.py, FastAPI/app/services/llm.py:152, FastAPI/app/models/__init__.py:245.
- Приёмка: два канала с разными промптами дают ожидаемые разные результаты; группа анализирует только новые сообщения по своему промпту; повторный цикл и цикл без новых сообщений соответствуют выбранному режиму; результат сохраняется после перезапуска.

## Фаза 2. Надёжность обработки до публичного запуска

### 9.1. Не терять доставку после сбоя

- Красный сценарий: сохранить дедупликацию, прервать процесс до доставки, перезапустить; сообщение должно оставаться доступным для доставки.
- Согласовать контракт повторов. Проработать устойчивую запись намерения доставки в той же транзакции, что и принятие сообщения, независимые состояния n8n/бота и ограниченные повторы. Новая схема только миграциями.
- Стабильный ID события передавать получателю; для n8n проверить обработку повторов. Не обещать exactly-once для внешней системы без её участия: таймаут после успешного приёма создаёт неопределённость.
- Исправить статус: сбой только Telegram-бота не должен выглядеть как SUCCESS. Ошибка аватарки не должна лишать пользователя поста.
- Источники: FastAPI/app/services/dedup.py:103, FastAPI/app/worker.py:325, FastAPI/app/services/dispatch.py:114, FastAPI/app/services/dispatch.py:259.
- Приёмка: сбои до/после внешнего ответа и перезапуск не теряют работу; повторы имеют согласованное поведение, успешный канал доставки не повторяется из-за сбоя другого.

### 9.2. Соблюдать FloodWait

- Красный сценарий: Telegram просит 3600 секунд; следующие тики и перезапуск не обращаются к ограниченному аккаунту до разрешённого времени.
- Сохранять срок следующей попытки на нужном уровне аккаунта/операции, проверять и очередь, и расписание; другие пользователи продолжают работать.
- Источники: FastAPI/app/worker.py:281, FastAPI/app/services/tg_pool.py:160, FastAPI/tests/test_58_worker_body.py:387.
- Приёмка: никакого раннего повтора и длительного ожидания внутри общего тика; интерфейс показывает отложенное состояние, а не фиктивный успех.

### 9.3. Изолировать ошибки мониторов

- Проверить гипотезу красным сценарием: два просроченных монитора, первый падает и вызывает rollback, второй должен обработаться, затем должна пройти очистка.
- При подтверждении устранить чтение истёкших ORM-объектов после rollback через изоляцию транзакций/повторную загрузку. Проверить на настоящем Postgres, а не только SQLite.
- Источники: FastAPI/app/worker.py:234, FastAPI/app/worker.py:239, FastAPI/app/worker.py:252; FastAPI/tests/test_58_worker_body.py.
- Приёмка: отказ одного канала не обрывает обслуживание остальных пользователей; очередь, расписание и очистка сохраняют работоспособность.

### 9.4. Защитить стандартные логи и границы тенантов

- Красный тест захватывает stdout/stderr и traceback с синтетическим секретом. Сейчас очистка jobs.error не охватывает logger.warning(exc_info=True).
- Обеспечить очистку всех каналов логирования; проверить URL Telegram Bot API, Authorization, строки подключения и текст исключений.
- Привести тенантные операции worker/gateway/dispatch к TenantRepo, отделив необходимые глобальные операции планировщика. Наличие ручного фильтра само по себе не доказывает утечку, но нарушает протокол проекта.
- Источники: FastAPI/app/worker.py:172, FastAPI/app/worker.py:405, FastAPI/app/db.py:48, FastAPI/app/services/journal.py, FastAPI/AGENTS.md.
- Приёмка: синтетические секреты отсутствуют во всех логах; задачи двух пользователей не читают и не отправляют чужие данные.

## Порядок и уверенность

8.1 и 8.2 -> 8.3-8.6 -> 9.1-9.4 -> 10.1-10.3. Первый пользовательский запуск проверяется с Google, Postgres и работающим worker. Открытие регистрации для других пользователей следует после полной приёмки изоляции и надёжности. Для личного этапа предлагается ограничить доступ владельцем на сервере; учётная запись владельца подтверждена для переноса.

Предлагаемые инженерные ориентиры первой версии, подлежащие проверке нагрузочным прогоном:

- Первый запуск для одного активного пользователя. Количество источников и объём сообщений задаёт пользователь без продуктовых квот; производительность измеряется на его конфигурации. Страницы API и батчи обработки ограничиваются технически для устойчивости, сохраняя возможность обработать весь выбранный объём. Уже обработанные сообщения в LLM повторно не отправляются.
- Один постоянный worker без сна при отсутствии HTTP-трафика; расписания разнести по времени, чтобы избежать одновременного старта всех каналов. API и БД размещать близко друг к другу.
- При исправных внешних API целевой старт 95% запусков не позднее 2 минут от расписания, результат не позднее 5 минут. При FloodWait и отказах явно показывать отсрочку; не обещать эти сроки независимо от внешних сервисов.
- Доставка с устойчивой очередью, стабильным ID события и повторами временных ошибок с увеличением интервала до 24 часов; затем видимая ошибка и ручной повтор. Постоянные ошибки авторизации не повторять вслепую; учитывать Retry-After.
- Цель восстановления worker после падения до 5 минут, диагностика отсутствия heartbeat дольше 2 минут. Это требования к настройке и проверке, не уже действующие гарантии.
- Настройки и учётные данные не удаляются автоочисткой. Предложение по истории запусков: 30 дней с возможностью изменить; резервная копия БД ежедневно, проверенный сценарий восстановления, целевая потеря при аварийном восстановлении не более 24 часов.
