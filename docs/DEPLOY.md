# Развёртывание: фронтенд на Vercel, бэкенд на Railway

## Схема

```
браузер ──► Vercel (статика + переписывание /api, /auth) ──► Railway: web
                                                              Railway: worker
                                                              Railway: Postgres
```

Два процесса Railway из одного образа — `web` (`uvicorn app.main:app`) и
`worker` (`python -m app.worker`), общий Postgres. Фронтенд — статические файлы
из `static/`, без сборки.

## Почему запросы идут через переписывание Vercel, а не напрямую

`*.vercel.app` и `*.up.railway.app` — разные регистрируемые домены, оба в
Public Suffix List. Общей cookie между ними не бывает даже в принципе, поэтому
прямой вызов фронтенда к API — межсайтовый запрос:

- cookie с `SameSite=Lax` браузер в таком запросе **не отправляет вовсе** —
  пользователь просто разлогинен;
- `SameSite=None; Secure` отправляется, но это сторонняя cookie: **Safari
  блокирует такие по умолчанию**, Chrome сворачивает их поддержку.

Переписывание на стороне Vercel убирает проблему целиком: браузер видит один
origin, cookie остаются первой стороной, CORS не нужен. Цена — один сетевой
переход и расход функций Vercel.

**Прямой режим поддержан** (CORS + `SameSite=None`), но включается явно и не
работает в Safari. Годится, только если фронтенд и API стоят на поддоменах
одного домена — `app.example.com` и `api.example.com`. Тогда это уже не
межсайтовый запрос, и режим равноценен переписыванию.

## Настройка

### Railway — сервис `web`

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` |
| `APP_ENCRYPTION_KEY` | `openssl rand -base64 32` — **менять нельзя**, см. ниже |
| `SECRET_KEY` | `openssl rand -base64 32` |
| `ENVIRONMENT` | `production` |
| `APP_BASE_URL` | адрес **фронтенда** — по нему строится ссылка в письме сброса |
| `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` | с my.telegram.org |
| `RESEND_API_KEY` | почта для сброса пароля |
| `FRONTEND_ORIGINS` | **пусто** в режиме переписывания; список origin через запятую в прямом режиме |
| `API_ORIGIN` | публичный адрес API — по нему определяется, межсайтовый ли запрос |

Миграции применяет только `web` (`preDeployCommand` в `railway.json`): если их
запустят оба сервиса, они пойдут одновременно.

### Railway — сервис `worker`

Те же переменные, команда `python -m app.worker`, **без** `preDeployCommand`.

### Vercel

1. Корень проекта — каталог `FastAPI` (или переместите `static/` в отдельный
   репозиторий фронтенда).
2. В `vercel.json` заменить `REPLACE-WITH-RAILWAY-HOST` на адрес сервиса `web`.
3. Build Command пустой, Output Directory — `static`.

### Вход через Google (необязательно)

Функция выключена, пока не заданы **все три** переменные — кнопка на страницах
входа скрыта, а CSP не пускает сторонние origin. Включение — три шага, и
пропуск третьего даёт молчаливую поломку: кнопка появится, а браузер откажется
грузить SDK.

1. **Railway (`web` и `worker`)** — публичные значения из настроек
   веб-приложения в консоли Firebase:

   | Переменная | Пример |
   |---|---|
   | `FIREBASE_API_KEY` | `AIzaSy...` |
   | `FIREBASE_AUTH_DOMAIN` | `<project>.firebaseapp.com` |
   | `FIREBASE_PROJECT_ID` | `<project>` |

   Это публичные значения: `apiKey` идентифицирует проект, а не даёт доступ —
   защищают правила и список разрешённых доменов. Приватный ключ **сервисного
   аккаунта** сюда не попадает: его читает `firebase_admin` из
   `GOOGLE_APPLICATION_CREDENTIALS`.

2. **Firebase console → Authentication → Settings → Authorized domains** —
   добавить домен Vercel. Без этого popup входа закроется с ошибкой.

3. **`vercel.json`** — расширить CSP. Фронтенд на Vercel отдаётся статикой со
   своим заголовком, и он не знает о настройках Railway: политика остаётся
   узкой по умолчанию и расширяется руками ровно тогда, когда функция нужна.
   В `Content-Security-Policy` дописать:

   ```
   script-src 'self' https://www.gstatic.com https://apis.google.com;
   connect-src 'self' https://identitytoolkit.googleapis.com https://securetoken.googleapis.com;
   frame-src https://accounts.google.com https://<project>.firebaseapp.com
   ```

   `'unsafe-inline'` не добавлять ни при каких обстоятельствах — Firebase его
   не требует, а он вернул бы исполнение инлайн-скриптов.

## Проверка после первого деплоя

1. `GET /health` через адрес Vercel → `{"status":"ok"}` (переписывание работает).
2. Регистрация → вход → перезагрузка страницы: сессия жива (cookie первой стороны).
3. Любое изменение (добавить канал) → проходит (CSRF-заголовок доезжает).
4. Сброс пароля → ссылка в письме ведёт на домен Vercel, а не на Railway.
5. Редеплой `web` → повторная авторизация в Telegram **не** требуется:
   сессия лежит в базе зашифрованной, а не в файле.
6. Воркер: добавить канал → «Запустить» → в течение полуминуты появляется
   запись в ленте и в журнале. Пустая лента при статусе задачи `pending`
   означает, что сервис `worker` не поднят.
7. Если включён вход через Google — кнопка видна на `/login`, и в консоли
   браузера нет ошибок CSP (иначе не выполнен шаг 3 выше).

## Чего нельзя делать

**Менять `APP_ENCRYPTION_KEY` после первого запуска.** Им зашифрованы
MTProto-сессии пользователей: новая пара ключей делает их нечитаемыми, то есть
выбрасывает всех из подключённых Telegram-аккаунтов. Ротация — отдельная
процедура с перешифровкой, а не смена переменной.

**Выдавать `Access-Control-Allow-Origin: *`.** Вместе с учётными данными
браузер такое сочетание отвергает, а если бы принимал — API с сессионными
cookie был бы открыт любому сайту. Список origin задаётся поимённо.
