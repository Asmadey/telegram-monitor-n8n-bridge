# Перенос старой базы и Telegram-сессии

Скрипт дополняет существующее приложение. Он не удаляет источник и не заменяет
существующие настройки или Telegram-аккаунт в Postgres. Владелец определяется
по подтверждённому Google email; при Google-входе используется тот же пользователь.

Перед переносом остановите прежний процесс Telegram и оставьте новый worker
выключенным. Одного отсутствия открытого файла недостаточно, если прежний процесс
уже загрузил ключ в память. Одновременное использование ключа разными процессами
может аннулировать Telegram-сессию.

Сначала сделайте резервную копию Postgres средствами Railway. Снимки SQLite
создавайте через SQLite backup API после остановки записи, а не копированием
файла с незавершённым WAL. Храните снимки базы и сессии только зашифрованными вне
репозитория; ключ шифрования берите из защищённого окружения Railway, не из чата
или командной строки. Оригиналы сохраняются до проверки результата.

В защищённом окружении должны быть DATABASE_URL и APP_ENCRYPTION_KEY.
Ключи приложения (`--verify-telegram`) берутся из кабинета владельца; если
кабинет ещё пуст, задайте оператору TELEGRAM_API_ID и TELEGRAM_API_HASH —
это запасной путь, а не рабочая настройка сервиса. Не передавайте DATABASE_URL через аргументы
процесса. APP_ENCRYPTION_KEY должен совпадать с ключом API и worker.

```sh
python -m scripts.migrate_sqlite_to_pg \
  --user-email owner@example.com \
  --sqlite-path /secure/source/storage.db \
  --telegram-session-path /secure/source/personal_account.session \
  --verify-telegram
```

`--verify-telegram` разрешает короткое подключение с StringSession в памяти,
получение профиля и отключение в finally. Запрос кода входа не выполняется.
Источник `.session` открывается только для чтения. Повторный импорт не заменяет
уже подключённый аккаунт и не восстанавливает устаревшие настройки поверх новых.

Перенос включает мониторы, историю прочитанных ID, ленту, журналы, настройки
интеграций и автоочистки, зашифрованную Telegram-сессию. Исходные строки settings
также сохраняются зашифрованными в legacy_import_rows. Журналы очищаются от
известных форм токенов. Квитанции переноса журналов записываются в той же транзакции,
что и сами строки: повторный запуск не удваивает их. Старые фото в ленте остаются
в резервной копии источника; новое приложение загружает аватарки отдельно.

Перед запуском по базе, куда уже переносили данные старой версией скрипта,
сверьте историю: старый скрипт не создавал квитанции журналов. Без такой сверки
первый запуск обновлённого скрипта может повторить старые журналы. Один владелец
и один источник на серию повторных запусков; объединение нескольких разных
SQLite-файлов одного владельца требует отдельного сопоставления исходных ID.

После переноса сверяйте счётчики и содержимое в приложении, входя через Google:
каналы и промпты, настройки без раскрытия ключей, ленту и состояние Telegram.
Повторный перенос должен вернуть нулевые счётчики вставок. Только после этого
запускайте новый worker. Живой Telegram/LLM/n8n проверяется отдельно от переноса.
