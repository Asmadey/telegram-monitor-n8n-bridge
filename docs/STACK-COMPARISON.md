# Выбор стека для шаблона «Build New»

Сравнительный анализ вариантов пересборки шаблона. Документ для самостоятельного изучения — с цифрами, компромиссами и моими комментариями.

Дата: 7 августа 2026
Отправная точка: Rails 8 + Inertia.js + React 19 + PostgreSQL (текущий репозиторий)

---

## 0. Краткий вывод (если читать только один абзац)

**Решающий фактор — не производительность, а то, насколько тебе комфортно в Ruby.**

Если Ruby тебя не раздражает — **оставайся на Rails**. Текущий шаблон объективно хорош, полностью готов, и миграция съест 3–5 недель ради выигрыша, который на реальной нагрузке ты не увидишь.

Если Ruby — это язык, в который ты не хочешь погружаться, и каждое изменение бэкенда будет борьбой — **тогда миграция на Next.js 16 фуллстек окупается**, но окупается она удобством разработки, а не скоростью работы приложения.

Вариант с Go я бы не брал для стартового шаблона. Подробности — ниже.

## 2. Производительность — честные цифры

Порядки величин, не бенчмарк. Простой JSON-эндпоинт, одно ядро:

| Стек | req/s (пустой роут) | req/s (**реальная страница с запросом в Postgres**) | Память на процесс | Холодный старт |
|---|---|---|---|---|
| **Go (chi/echo)** | ~60 000–100 000 | **~400–900** | ~20–40 МБ | ~10 мс |
| **Node + Hono/Fastify** | ~20 000–45 000 | **~350–800** | ~80–150 МБ | ~200 мс |
| **Node + Express** | ~8 000–15 000 | **~300–700** | ~90–160 МБ | ~200 мс |
| **Next.js (App Router, SSR)** | ~3 000–8 000 | **~200–500** | ~150–300 МБ | ~500 мс |
| **Rails 8 + Puma** | ~1 500–4 000 | **~200–500** | ~250–400 МБ | ~2–5 с |

> 💬 **Комментарий — самое важное в этой таблице.** Посмотри на разницу между второй и третьей колонкой. В синтетическом тесте Go быстрее Rails в **30 раз**. На реальной странице, которая ходит в базу — **в 1.5–2 раза**. Потому что узкое место — это Postgres, сеть и рендеринг React, а не рантайм.
>
> Практический смысл: чтобы разница Go vs Rails стала заметна пользователю, тебе нужно ~500+ req/s устойчиво. Это примерно 10–40 млн запросов в сутки. Если ты не там — выбор языка по производительности это оптимизация того, что не является проблемой.
>
> Где Go **действительно** выигрывает: память (в 10 раз меньше = дешевле хостинг), CPU-bound задачи (обработка изображений, парсинг, криптография), холодный старт, деплой одним бинарником без рантайма.

Для стартового шаблона, цель которого — «никогда больше не тратить неделю на аутентификацию», это прямое противоречие цели.

## 4. База данных

Сначала важное уточнение: **Redis — не альтернатива Postgres.** Это in-memory хранилище для кэша, очередей и сессий; данные в нём эфемерны по умолчанию. Сравнивать «Redis или Postgres» — это как «шина или автомобиль». Реальный выбор основной БД: **Postgres vs SQLite vs MySQL**.

| | **PostgreSQL** | **SQLite (или Turso/libSQL)** | **MySQL** |
|---|---|---|---|
| Скорость чтения | быстро | **быстрее всех** (нет сети) | быстро |
| Параллельные записи | **отлично** | ⚠️ слабое место (одна запись за раз) | отлично |
| Работает на Vercel / serverless | **да** | ❌ нет (ФС эфемерна) → нужен Turso | да |
| Несколько инстансов приложения | **да** | ❌ нет (файл на одном диске) | да |
| `LISTEN/NOTIFY` (realtime) | **да** | нет | нет |
| JSONB + индексы по JSON | **отлично** | базово | средне |
| Полнотекстовый поиск | **отлично** (`tsvector`) | FTS5 (хорошо) | средне |
| Очереди задач на той же БД | **pg-boss / river** | ⚠️ мало решений | мало решений |
| Сложность эксплуатации | средняя | **минимальная** (один файл) | средняя |
| Бэкап | pg_dump | **копирование файла** | mysqldump |

### Нужен ли Redis отдельно?

| Задача | С Postgres | С Redis |
|---|---|---|
| Кэш | Next Data Cache / таблица | быстрее, но +1 сервис |
| Очереди задач | pg-boss ✅ | BullMQ (быстрее на 10k+ job/с) |
| Сессии | таблица `sessions` ✅ | быстрее на чтение |
| Rate limiting | таблица + окно | ⚠️ Redis тут реально лучше |

> 💬 **Мой ответ на твой вопрос: бери PostgreSQL, Redis не добавляй.**
>
> Причины конкретно для твоего случая:
> 1. **Это и есть лучшая идея текущего шаблона.** Rails 8 положил очереди, кэш и WebSockets в тот же Postgres — и убрал целый сервис из инфраструктуры. `pg-boss` воспроизводит это в Node один-в-один. Терять этот принцип при миграции было бы обидно.
> 2. **SQLite не сочетается с Next.js на Vercel** — файловая система эфемерна, инстансов много. SQLite отличен, если ты деплоишь на один VPS (Hetzner, Railway, Coolify) и точно не масштабируешься горизонтально. Это осознанный выбор «простота против гибкости», и назад с него ехать больно.
> 3. **Redis добавляй позже и только когда упрёшься.** Один сервис = одна вещь, которая может упасть в 3 часа ночи. Пока ты не делаешь >5000 job/с или жёсткий distributed rate limiting — Postgres закрывает всё.
>
> Исключение: если ты **точно** знаешь, что деплой будет на один сервер и приложение персональное/малонагруженное — SQLite даст самый простой в жизни деплой. Но тогда и Next.js на Vercel отпадает.

## 5. SEO — что сейчас работает и как это не потерять

Ты прав: **в текущем шаблоне SEO сделан действительно хорошо.** Это одна из самых недооценённых частей репозитория. Вот полный аудит и паритет:

| Элемент | Rails (сейчас) | Next.js 16 | React SPA + Vite |
|---|---|---|---|
| SSR (краулер видит HTML) | ✅ Node-сайдкар :13714 | ✅ **из коробки, без сайдкара** | ❌ пустой `<div id="app">` |
| Streaming / частичный рендер | ❌ | ✅ (RSC + Suspense) | ❌ |
| `title` + `description` на странице | ✅ правило в CLAUDE.md | ✅ `generateMetadata` | ⚠️ react-helmet |
| `og:title` / `og:description` | ✅ обязательны по правилу | ✅ типизировано | ⚠️ руками |
| `og:image` генерируемые | ❌ | ✅ **`ImageResponse`, динамические** | ❌ |
| `sitemap.xml` | ✅ sitemap_generator | ✅ `sitemap.ts` (типизирован) | ⚠️ скриптом |
| `robots.txt` | ✅ с Disallow для приватных | ✅ `robots.ts` | ⚠️ статикой |
| `llms.txt` (AI-краулеры) | ✅ **редкая и правильная вещь** | ✅ переносится | ✅ переносится |
| JSON-LD / Schema.org | ❌ не реализовано | ✅ легко добавить | ⚠️ |
| `hreflang` для локалей | ❌ (i18n нет) | ✅ next-intl автоматом | ⚠️ руками |
| Canonical URL | ❌ не реализовано | ✅ в metadata | ⚠️ |
| Core Web Vitals | средне (гидратация всего) | ✅ **лучше (RSC = меньше JS)** | хуже |

> 💬 **Комментарий.** Next.js здесь не «не хуже», а **объективно лучше Rails+Inertia**: SSR без отдельного Node-процесса, React Server Components отправляют клиенту меньше JavaScript (прямое влияние на LCP/INP), динамические og-картинки, типизированные метаданные.
>
> **Три вещи, которых сейчас нет и которые стоит добавить при переписывании:** JSON-LD (`Organization`, `Product`, `FAQPage` — влияет на rich snippets в выдаче), `canonical`, и генерируемые og-изображения.
>
> **Правило из `CLAUDE.md` про обязательные 4 метатега на каждой странице — обязательно перенеси.** Это ровно тот тип правила, который заставляет AI-агента не забывать SEO. Оно ценнее, чем любая библиотека.
>
> ⚠️ **И главное: вариант E (React SPA + Vite) уничтожает весь этот слой.** Если SEO для тебя важен — Vite-SPA отпадает автоматически, независимо от остальных соображений.

## 6. Syntux — стоит ли зашивать в шаблон

**Что это.** Библиотека генеративного UI. Ты передаёшь ей значение (`value`) и подсказку (`hint`), LLM в рантайме генерирует JSON-DSL («React Interface Schema»), который рендерится в React-компоненты. Поддержка Next.js и React Router; есть стриминг и кэширование.

**Состояние проекта:** 487 звёзд · 20 форков · MIT · создан 18 декабря 2025 · последний коммит 16 мая 2026 (~3 месяца тишины).

| Сценарий | Годится? | Почему |
|---|---|---|
| **Лендинг / маркетинг** | ❌ **категорически нет** | Недетерминированный HTML, задержка LLM до первого байта, разный контент при каждом заходе. Google не индексирует то, что нестабильно. Прямое разрушение раздела 5. |
| **Публичные страницы продукта** | ❌ нет | Те же причины + стоимость токенов на каждый показ |
| **Внутренние дашборды** | 🟡 возможно | Твоя интуиция верна — здесь SEO не нужен |
| **Админка / просмотр данных** | 🟡 возможно | Осмысленно для «покажи мне этот JSON красиво» |
| **Ядро стартового шаблона** | ❌ **нет** | См. ниже |

> 💬 **Мой вердикт: твоя интуиция полностью верна, но я бы пошёл дальше — не зашивай его в шаблон вообще.**
>
> Дело не только в SEO. Три причины:
>
> 1. **Возраст и поддержка.** Библиотеке 8 месяцев, 487 звёзд, 3 месяца без коммитов. Стартовый шаблон — это фундамент на годы; в фундамент не кладут зависимость, которая может быть заброшена. Дизайн-система, Radix, Drizzle — это ставки на десятилетие. Syntux — ставка на эксперимент.
> 2. **Конфликт с твоей дизайн-системой.** У тебя 5 936 строк тщательно собранных примитивов с токенами и живой документацией. Смысл дизайн-системы — детерминированная консистентность. Смысл генеративного UI — обратное. Это два взаимоисключающих подхода в одном репозитории.
> 3. **Цена и латентность.** Каждый рендер = вызов LLM. Даже с кэшем: первый показ каждого нового варианта данных — это секунды ожидания и деньги. Для дашборда, который открывают 200 раз в день, это ощутимо.
>
> **Что я бы сделал вместо:** оставь его как *опциональный рецепт* — отдельная страница в `docs/`, описывающая, как подключить syntux к конкретному внутреннему дашборду, если он понадобится. Ноль стоимости, ноль риска, возможность есть. Зашивать в ядро — нет.

## 7. Аргументы за то, чтобы остаться на Rails

Раздел, который стоит прочитать внимательно, потому что он идёт против твоего изначального запроса.

**За то, чтобы остаться:**

- Всё уже работает: аутентификация, админка, дизайн-система, SSR, SEO, CI из 5 джобов, деплой на Hatchbox, изоляция БД по git-worktree
- Экономия 3–5 недель, которые можно потратить на собственно продукт
- Rails 8 — самый плотный «фреймворк на строку кода» из существующих. `rate_limit to: 10, within: 3.minutes` — одна строка вместо дня работы
- Solid-трифекта: очереди + кэш + WebSockets на одном Postgres без Redis
- Стабильность API: Rails почти не ломает обратную совместимость. Next.js за последние 3 года переписал модель роутинга и кэширования дважды
- Ноль риска регрессий — переписывание аутентификации с нуля это всегда потенциальные дыры в безопасности

**Против:**

- Два языка. AI-агенту приходится переключать контекст, а тебе — держать в голове две системы правил
- Ruby медленнее в рантайме (но см. раздел 2 — на практике почти не важно)
- Нет сквозной типизации от схемы БД до React-пропсов: изменил колонку — TypeScript не заметит
- Экосистема JS больше, интеграций с AI/LLM-инструментами больше
- Если Ruby для тебя чужой язык — каждое изменение бэкенда будет тормозить работу

> 💬 **Комментарий, самый честный в документе.**
>
> Я не могу решить это за тебя, потому что решающая переменная — не техническая. Вопрос звучит так: **«Когда мне нужно поменять что-то в бэкенде, я открываю Ruby-файл спокойно или с раздражением?»**
>
> Если спокойно — оставайся. Технических причин уходить нет. Ты потратишь месяц, чтобы получить приложение, которое работает так же.
>
> Если с раздражением — уходи, и не переживай про производительность. Ты покупаешь не скорость приложения, а скорость своей работы. Это абсолютно валидная причина, просто нужно называть её честно, а не подводить под неё технические аргументы, которые на самом деле не решают.
>
> Отдельно: аргумент «AI-агент лучше пишет TypeScript, чем Ruby» — реальный и, возможно, для тебя главный. Единый TS-стек от Drizzle-схемы до React-компонента даёт агенту цельную типизированную картину, где ошибка ловится компилятором, а не в проде. Это стоит месяца работы, если ты строишь много проектов на этом шаблоне.

## 8. Итоговые рекомендации по вариантам

| Твоя ситуация | Что брать |
|---|---|
| Ruby не мешает, нужно быстро выпускать продукты | **Остаться на Rails 8.** Ничего не переписывать |
| Хочу единый TS-стек, важны SEO и скорость разработки | **Next.js 16 фуллстек** + Postgres + Drizzle + better-auth + pg-boss + next-intl |
| Нужен максимум производительности, готов платить сложностью | **Next.js + Go API** — но только если у тебя реально >500 req/s |
| Нужен только внутренний инструмент, SEO не важен | React SPA + Vite + Hono. Быстро и просто |
| Деплой на один VPS, приложение небольшое | Next.js + **SQLite** вместо Postgres |

### Если выбираешь Next.js — финальный рекомендованный набор

```
Next.js 16 (App Router, Turbopack)   — фреймворк, SSR, SEO
TypeScript                           — один язык на весь стек
Tailwind CSS v4                      — остаётся как есть, миграции нет
Radix UI                             — уже используется, переносится 1:1
PostgreSQL + Drizzle ORM             — БД + сквозные типы
better-auth                          — сессии, пароли, сброс
pg-boss                              — очереди на том же Postgres, без Redis
next-intl                            — i18n с поддержкой RSC и hreflang
Nodemailer + react-email + Mailpit   — почта
Vitest + Playwright                  — тесты
```

Изменения относительно твоего изначального запроса и причины:

| Ты просил | Рекомендую | Почему |
|---|---|---|
| Vite | Turbopack (внутри Next) | Next.js не работает с Vite — свой бандлер |
| Tailwind v3 | **Tailwind v4** | Дизайн-система уже на v4; даунгрейд = день работы ради более медленной сборки |
| Express | не нужен вовсе | При Next-фуллстеке отдельный бэкенд не нужен. Если всё же нужен — Hono, не Express |

## 10. Что перенести из текущего шаблона независимо от выбора

Вещи, которые сделаны правильно и которые легко потерять при переписывании:

1. **Правило четырёх метатегов** на каждой странице (title, description, og:title, og:description) — записано в `CLAUDE.md`, дисциплинирует агента
2. **`llms.txt`** — редкая и правильная вещь, AI-краулеры читают его напрямую
3. **Принцип «одна база для всего»** — очереди, кэш, сессии в Postgres, без Redis
4. **Изоляция БД по git-worktree** (`config/database.yml`) — параллельные агенты не затирают схемы друг друга
5. **Правило «не запускай проверочный сервер на порту 3000»** — порт 3000 зарезервирован под ручной просмотр
6. **Живая документация дизайн-системы** на `/admin/design-system` — 20 секций, показывающих агенту точную разметку
7. **Правило «используй голый семантический HTML»** — `<h1>` без утилит Tailwind, стили в базовом слое
