## Команды

Все команды выполняются из корня репозитория. Окружение: `.venv`.

```bash
.venv/bin/python -m pytest -q                        # все тесты
.venv/bin/python -m pytest tests/test_02_xss.py -q   # один файл
.venv/bin/python -m pytest tests/test_02_xss.py::test_scanner_sees_through_nested_template_literals -q  # один тест

.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload  # веб
.venv/bin/python -m app.worker                       # воркер (второй процесс)
# Локально ни то, ни другое не поднимется: в `.env` лежат только ключи Telegram,
# а APP_ENCRYPTION_KEY и DATABASE_URL живут в переменных Railway. Приложение
# падает громко и по делу — это защита, а не поломка. Проверять — тестами.

.venv/bin/pip install -r requirements-dev.txt       # зависимости (app+dev)

# Схема БД — только через Alembic (Фаза 1, задача 1.4):
.venv/bin/alembic upgrade head                        # применить миграции
.venv/bin/alembic revision --autogenerate -m "..."    # новая ревизия (проверить файл глазами!)

# Перенос старых данных из SQLite в Postgres (задача 1.5; без APP_ENCRYPTION_KEY откажется работать):
.venv/bin/python -m scripts.migrate_sqlite_to_pg --user-email owner@example.com

ruff check . && ruff format --check .   # линтер (пакеты Фазы 1)
mypy app/                               # типы
```

Запуск через Docker: `docker build -t teleton .` (Dockerfile в корне репозитория). Railway: `railway.json`, healthcheck `/health`.

## Архитектура (big picture)

**Что это:** мониторинг Telegram-каналов от лица живого аккаунта через MTProto (Telethon), дедупликация постов, анализ через OpenRouter LLM, доставка в n8n-вебхук и Telegram-бота. Сейчас — персональный инструмент; **цель (`docs/PLAN.md`) — мульти-тенант SaaS на Railway**. Стек не меняется: FastAPI + Telethon; из Rails-шаблона переносятся паттерны (сессии в БД, сброс пароля, админка), а не код. **Каталог `Ruby/` удалён 2026-09-10** (уборка дерева): апстрим — `https://github.com/buildermethods/build-new.git`, полный архив с историей и местными правками — `private-backups/ruby-template-2026-09-10.tar.gz`, а уникальный разбор стека спасён в `docs/STACK-COMPARISON.md`. Ссылки вида `Ruby/app/models/session.rb` в коде и в `docs/PLAN.md` указывают на этот апстрим.

**Текущее состояние (сверено 2026-09-10). Монолита больше нет** — `server.py`
удалён задачей 7.4. Всё, что ниже, проверено в дереве, а не по памяти:

- `app/` — бэкенд: `config` (единственная точка чтения ENV, `.env` никогда не
  пишется), `db`, `deps`, `models` (**17 таблиц**, `user_id` NOT NULL + FK +
  индекс), `security`, `api` (роутеры), `services`, `worker`. Postgres, схема —
  только Alembic (14 ревизий, head `0014`).
- `static/` — SPA без сборки: `index.html` — 752 строки разметки, логика в
  **11 модулях** `static/js/` (~3600 строк). Инлайновых обработчиков нет: их
  запрещает CSP (`script-src 'self'`), задача 9.8.
- **Два процесса из одного образа** (`Procfile`): `web` — `uvicorn app.main:app`,
  `worker` — `python -m app.worker`. Долгоживущие Telethon-клиенты **только у
  воркера**, иначе `AUTH_KEY_DUPLICATED`.
- Прод: бэкенд на Railway (`https://web-production-d2e997.up.railway.app`),
  фронтенд на Vercel, `/api` и `/auth` проксируются на Railway.

**Предметная модель (Фаза 11) — источник, а не канал.** Главный объект —
**источник**: задача поиска. У него N каналов (до 10), у каждого канала **свой
лимит сообщений и свой промпт извлечения**; у источника — общий промпт
оформления и стоп-слова. Прогон идёт конвейером **map → reduce**: разбор по
каждому каналу отдельно, затем сведение. Имена таблиц исторические и наружу не
видны: `monitors` — это источники, `monitor_channels` — их каналы. **Во всём,
что видит пользователь, одно слово: «источник».**

**Ключевой факт, определяющий приоритеты:** на сервере оседают MTProto-сессии чужих Telegram-аккаунтов — их нельзя сбросить удалённо, утечка = компрометация всех аккаунтов разом. Поэтому «сначала работает, потом безопасно» здесь не действует.

## Крайне важные факты

Каждый стоил отдельного разбора. Незнание любого из них ломает прод или данные.

1. **`APP_ENCRYPTION_KEY` — единственный ключ ко всем секретам тенантов.** Им
   зашифрованы `session_string_encrypted` (MTProto-сессии), `api_hash`,
   ключ OpenRouter, токен бота, URL вебхука, полезная нагрузка задач. **Потеря
   ключа = потеря всех этих данных навсегда**, расшифровать нечем. Ключ живёт в
   переменных Railway, в репозитории и в `.env` его нет. У воркера есть отпечаток
   (`key_fingerprint`) — защита от тихой подмены ключа.
2. **Миграции выполняются ДО старта нового кода.** `railway.json` →
   `preDeployCommand: alembic upgrade head`, то есть схему меняет старый
   работающий код. Поэтому **удаление колонки и её создание — разные ревизии в
   разных релизах** (expand/contract). Одна ревизия, которая создаёт и удаляет
   разом, даёт минуту 500-х. `downgrade` намеренно бросает исключение: миграции
   только вперёд.
3. **Docker — боевой путь, а не запасной.** `railway.json` собирает
   `builder: "DOCKERFILE"`, `Dockerfile` делает `COPY . .`. Всё, чего нет в
   `.dockerignore`, уезжает в боевой образ. **`.gitignore` ≠ `.dockerignore`** —
   это разные файлы с разными списками, и проверка списка шаблонов не заменяет
   живую сборку (77 МБ кеша mypy нашлись только настоящим `docker build`).
4. **`AsyncSession` не рассчитан на одновременные операции.** Отсюда
   последовательные проходы разбора вместо параллельных. И: **`rollback()`
   аннулирует ВСЮ сессию, а не один объект** — перед циклом с откатами поля
   снимаются в обычные словари, иначе второй виток падает на `MissingGreenlet`.
5. **Тесты — единственная работающая проверка.** Локально приложение не
   поднимается (см. «Команды»), живого Postgres на машине нет. Поведенческие
   тесты без него обязаны писать `pytest.skip`, а не молча зеленеть.

## Протокол сессии

1. Прочитать этот файл → `docs/PLAN.md` (раздел «Статус выполнения») → `AGENTS.md`.
2. Выполнять задачи **строго по порядку фаз** из `docs/PLAN.md`.
3. Каждая задача — цикл CDD: красный тест (обязан упасть на `assert`, не на `ImportError`) → минимальная реализация → зелёный → запись.
4. **После каждой выполненной задачи обновлять `docs/PLAN.md`:** чекбокс в разделе 12 + строка в «Статусе выполнения» (дата, что сделано, что не подтверждено). Не откладывать на конец сессии.
5. В конце задачи — запись в `PROGRESS.md` (формат — `AGENTS.md` §8).

## Порядок выкладки

**Владелец PR не вливает.** Ветка → PR → зелёный CI → **слияние делает агент**,
не оператор. Просить оператора «влить PR» — не просить, а перекладывать: он и так
сказал «деплой и продолжай». Если слияние заблокировано разрешениями среды —
сказать об этом прямо и одной строкой, какое правило нужно добавить, а не
оставлять PR висеть.

После слияния — проверить живой прод (`/health`, ключевой экран), а не считать
выкладку законченной по зелёному CI.

## Ключевые правила (полностью — в AGENTS.md)

- **CDD:** тест пишется до реализации и не ослабляется ради зелёного. Ошибка в тесте исправляется в тесте с объяснением (пример: XSS-тест на регулярках пропускал живой XSS из-за вложенных шаблонных литералов — переделан на сканер с self-test'ами).
- **Секреты** не попадают в чат, PR и репозиторий; всё, что попало в переписку, считается скомпрометированным. `.gitignore` ≠ `.dockerignore`.
- **БД:** схема меняется только миграцией Alembic; `ALTER TABLE` в коде приложения запрещён; запросы через `TenantRepo` (не писать `WHERE user_id = ...` руками).
- **Telethon:** долгоживущие клиенты только у воркера; сессии — `StringSession` в БД зашифрованно; `FloodWaitError` не ретраится сразу; лимит запросов кода авторизации — защита аккаунта клиента.
- **На чужих ресурсах всегда 404, не 403** (403 подтверждает существование объекта).
